# uxtest 시나리오 설명

Android 기기(CPH2749, 1272×2772)에서 일상 사용을 재현하면서 그동안 UFS 에 들어간 요청을 fsiotrace(`trace_type=fsio_ufs`)로 기록해요.
이 문서는 시나리오 60개가 **무엇을 하는지**와 **왜 이렇게 만들었는지**를 정리한 거예요.
정의 원본은 `scenarios/gen.py` 이고, agent 에는 같은 이름의 시나리오 템플릿으로 등록돼 있어요 (`pack.scenariopack.json`).

## 공통 규칙과 이유

| 규칙 | 이유 |
|---|---|
| 측정은 `trace_start` ~ `trace_stop` 구간만 | 앱 준비·정리 동작의 I/O 가 결과에 섞이지 않게 해요. 아래 "측정 구간"이 이 범위예요. |
| 회차는 기본 3회 (`repeatCount=3`) | 회차마다 trace job 이 따로 생겨 회차 간 편차를 볼 수 있어요. S5(3시간)·S6(6시간)만 1회예요. |
| trace 는 fsio_ufs 만, VFS·DRAM 없음 | 저장장치에 실제로 도달한 요청만 보려는 거예요. CPH2749 는 DRAM 대역폭을 지원하지 않아요. |
| cold 측정 전 `echo 3 > drop_caches` | 페이지 캐시에 남은 데이터 때문에 Read 가 사라지는 걸 막아요. |
| 앱 캐시 비우기 (Chrome·YouTube·Instagram 등) | 회차마다 같은 양의 썸네일·미디어 캐시 Write 가 나오게 해서 회차를 비교할 수 있게 해요. |
| 측정 끝에 `writeback 배수 대기` 3초 | 동작이 끝난 뒤 늦게 나가는 dirty page writeback 까지 담아요. |
| 화면 확인(`mCurrentFocus`)은 trace 를 멈춘 뒤에 | 확인용 dumpsys 의 I/O 가 측정을 오염시키지 않게 해요. |
| Perfetto·gfxinfo 결과는 tmpfs(`/dev/ux`)에 저장 | UFS 에 쓰면 그 Write 가 다음 측정에 섞여요. `run.py` 가 job 마다 PC 로 가져오고 지워요. |
| 촬영·녹음·다운로드 파일은 측정 후 삭제 | 저장 공간과 다음 회차의 상태를 같게 유지해요. 기존 사진은 건드리지 않아요. |
| 계정에 흔적이 남는 동작은 하지 않음 | 개인 계정 기기라서 좋아요·팔로우·검색 기록·메일 읽음 같은 것을 남기지 않아요 (탭 대신 스와이프, 검색 대신 좌표 인텐트 등). |
| text 스텝 앞에 키보드를 영문(Alphabet)으로 | `adb input text` 는 Gboard 가 한국어 모드면 영문을 자모로 바꿔요. `setup.sh --restore` 가 원래대로 되돌려요. |
| 셸 명령에 콤마를 쓰지 않음 | agent 가 콤마를 회차별 값 목록으로 잘라요. repeat>1 본 측정에서만 깨져요. |

**우선순위**: P1 = 먼저 잰 핵심 패턴, P2 = P1 을 보완하는 비교·변형, P3 = 대기(무선 adb, 긴 시간).

**측정에서 뺀 것**: Netflix(사용 안 함), Facebook 피드(로그아웃 상태이고 로그인하지 않음), F3 메시지(계정 연결 화면이 떠서 계정에 흔적이 남음).

## A. 앱 실행·전환

**왜 이 유형인가** — 앱을 켜고 오가는 건 가장 자주 하는 동작이에요. cold start 는 APK·odex·so 를 읽는 Random Read 가 몰리는 구간이라 Read Latency 가 체감 속도로 바로 이어져요. warm 전환·백그라운드 복귀는 cold 와 대비되는 기준선이에요.

### A1 Chrome cold start ×5 · P1
- **무엇을** — 페이지 캐시를 비우고 Chrome 을 강제 종료 후 실행하는 걸 5번 반복해요.
- **측정 구간** — [×5: 캐시 비우기 → Chrome cold start → 홈] → writeback 대기
- **왜** — 한 앱의 cold start 를 반복해 실행 Read 패턴이 얼마나 일정한지 봐요. 다른 A 시나리오의 기준이에요.
- **준비** — Chrome 첫 실행 화면을 끝내 둬요.

### A2 cold start 순회 6앱 · P1
- **무엇을** — Chrome → YouTube → 설정 → 갤러리 → 카메라 → 지도를 하나씩 캐시를 비우고 cold start 해요.
- **측정 구간** — 앱마다 [캐시 비우기 → cold start → 홈] × 6앱 → writeback 대기
- **왜** — 앱 크기·종류에 따라 실행 Read 양이 어떻게 다른지 봐요. Behavior 구간 이름으로 앱별 I/O 를 나눠 볼 수 있어요.
- **준비** — Chrome·갤러리 첫 실행 화면을 끝내 둬요.

### A3 3앱 왕복 전환 ×6 · P1
- **무엇을** — Chrome·YouTube·설정을 미리 띄워 둔 상태(warm)에서 앱을 오가며 짧게 스크롤해요 (3앱 × 2바퀴).
- **측정 구간** — [×2: Chrome 전환·스크롤 → YouTube 전환·스크롤 → 설정 전환·스크롤] → writeback 대기
- **왜** — 메모리에 남은 앱 사이를 전환할 때의 I/O 로, cold start(A1·A2)와 대비돼요. 백그라운드 동기화 영향으로 편차가 커요.

### A4 무거운 앱 cold start · P2
- **무엇을** — 지도·Facebook·Instagram 을 캐시를 비우고 실행만 해요.
- **측정 구간** — 앱마다 [캐시 비우기 → cold start → 홈] × 3앱 → writeback 대기
- **왜** — A2 보다 APK 가 큰 앱에서 실행 Read 가 얼마나 늘어나는지 봐요. Facebook 은 로그아웃 화면, Instagram 은 약관 화면까지라 첫 화면 실행 Read 만 담겨요.

### A5 최근 앱 화면 전환 ×6 · P2
- **무엇을** — 6개 앱을 띄워 둔 뒤 최근 앱 화면(`KEYCODE_APP_SWITCH`)에서 이전 앱 카드를 골라 여는 걸 6번 해요.
- **측정 구간** — [×6: 최근 앱 화면 → 이전 카드 → 열기 → 표시 대기] → writeback 대기
- **왜** — 실제 사용자가 가장 많이 쓰는 전환 방식이에요. 메모리에 남은 앱이라 Read 가 짧은 burst 로만 나와야 하고, 그렇지 않으면 앱이 메모리에서 밀려났다는 신호예요.

### A6 데이터 초기화 후 첫 실행 (날씨) · P2
- **무엇을** — 날씨 앱을 `pm clear` 한 직후 처음 실행해요.
- **측정 구간** — 초기화 후 첫 실행 → writeback 대기
- **왜** — 앱 데이터(DB·설정·캐시)를 처음 만드는 Write 를 봐요. A1(같은 앱 재실행)과 비교해요. Chrome 을 초기화하면 로그인·탭이 사라져서 계정 없는 날씨 앱을 골랐어요.

### A7 홈↔YouTube 복귀 ×10 · P2
- **무엇을** — YouTube 를 띄워 둔 채 홈과 앱을 10번 오가요.
- **측정 구간** — [×10: YouTube 복귀 → 홈 → 홈 대기] → writeback 대기
- **왜** — 앱이 백그라운드로 갈 때마다 상태를 저장하는 작은 Write 가 얼마나 나오는지 봐요.

### A8 백그라운드 5분 뒤 복귀 · P2
- **무엇을** — YouTube 를 띄운 뒤 Chrome·지도·카메라를 거쳐 5분 두고 돌아와요.
- **측정 구간** — 5분 뒤 YouTube 복귀 → 피드 스크롤 → writeback 대기
- **왜** — 메모리 압박 뒤 복귀가 warm 인지 cold 인지에 따라 Read 가 크게 달라요. 측정 전에 프로세스가 살아 있었는지(`YT_ALIVE`/`KILLED`)를 기록해 둘을 나눠 봐요.

## B. 웹·피드

**왜 이 유형인가** — 스크롤하는 동안 이미지·영상을 받아 디스크 캐시에 쓰는 작은 Write 가 계속 나와요. 앱마다 캐시 정책이 달라 같은 "스크롤"이라도 Write 양 차이가 커요. 피드 계열은 같은 횟수·간격으로 맞춰 앱끼리 비교할 수 있게 했어요.

### B1 Chrome 위키 로드+스크롤 · P1
- **무엇을** — Chrome 디스크 캐시를 비우고 영문 위키 문서 2개(SSD, Flash memory)를 열어 각각 8번 스크롤해요.
- **측정 구간** — 문서 1 열기·스크롤 → 문서 2 열기·스크롤 → writeback 대기
- **왜** — 웹 브라우징의 기본 패턴(HTTP 캐시 Write, SQLite 기록)이에요. 한글 URL 은 검색어로 처리돼서 ASCII URL 을 써요. 로그인 상태라 동기화 I/O 가 섞일 수 있어요.

### B1i Chrome 위키 (시크릿 모드) · P2
- **무엇을** — B1 과 같은 동작을 시크릿 탭에서 해요.
- **측정 구간** — 주소창 → 문서 1 → 스크롤 → 주소창 → 문서 2 → 스크롤 → writeback 대기
- **왜** — 시크릿은 HTTP 캐시·쿠키를 메모리에만 둬요. B1 대비 Write 가 얼마나 줄어드는지로 캐시 Write 의 몫을 가늠해요.

### B2 YouTube 검색+결과 스크롤 · P1
- **무엇을** — 이미지 캐시를 비운 YouTube 에서 검색한 뒤 결과를 스크롤해요.
- **측정 구간** — 검색 → 입력 → 결과 로딩 → 결과 스크롤 → writeback 대기
- **왜** — 썸네일을 새로 받아 쓰는 캐시 Write 를 봐요. 검색 바가 스크롤하면 숨어서 검색을 먼저 해요.

### B3 YouTube 홈피드 40회 · P1
- **무엇을** — 이미지 캐시를 비우고 홈피드를 1.5초 간격으로 40번 스크롤해요.
- **측정 구간** — 홈피드 스크롤 40회 → writeback 대기
- **왜** — 썸네일·미리보기 캐시 Write 가 이어지는 대표 피드 패턴이에요. B7·B7t 의 비교 기준이에요.

### B4 Chrome 탭 5개 열기+전환 · P2
- **무엇을** — 시크릿 탭 5개에 위키 문서를 열고 주소창 스와이프로 탭을 8번 오가요.
- **측정 구간** — 새 시크릿 탭·문서 열기 × 5 → 탭 전환 8번 → writeback 대기
- **왜** — 탭 상태 저장 Write 를 봐요. 개인 Chrome 의 기존 탭을 건드리지 않으려고 시크릿 탭을 써요. 종료하면 사라져요.

### B5 Chrome 이미지 많은 문서 · P2
- **무엇을** — 국기 이미지가 200여 개 있는 위키 문서를 캐시를 비우고 열어 30번 스크롤해요.
- **측정 구간** — 문서 열기 → 30번 스크롤 → writeback 대기
- **왜** — 글 위주 문서(B1)와 캐시 Write 양을 비교해 이미지가 Write 를 얼마나 늘리는지 봐요.

### B6 지도 이동·확대 10회 · P2
- **무엇을** — 좌표 인텐트로 서울시청을 열고 이동 5번, 두 번 탭 확대 5번을 해요.
- **측정 구간** — 좌표 열기 → 지도 로딩 → 이동 5번 → 확대 5번 → writeback 대기
- **왜** — 지도 타일 캐시 Read/Write 를 봐요. 검색 기록을 남기지 않으려고 검색 대신 좌표로 열어요. 위치 권한 창이 뜨면 선택하지 않고 닫기만 해요.

### B7 Instagram 홈 피드 40회 · P2
- **무엇을** — 이미지·영상 캐시를 비우고 홈 피드를 1.5초 간격으로 40번 스크롤해요.
- **측정 구간** — 홈 피드 스크롤 40회 → writeback 대기
- **왜** — B3(YouTube 홈피드)와 같은 횟수·간격으로 맞춰 앱별 캐시 Write 를 비교해요. 좋아요·팔로우가 남지 않게 탭은 하지 않아요.
- **준비** — Instagram 로그인

### B7r Instagram 릴스 20개 · P2
- **무엇을** — 캐시를 비우고 릴스 탭에서 5초씩 보며 20개를 넘겨요.
- **측정 구간** — 릴스 20개 넘기기 → writeback 대기
- **왜** — 짧은 영상 피드의 영상 캐시 Write 를 피드(B7)·YouTube 스트리밍(C1)과 비교해요. 두 번 탭하면 좋아요가 돼서 영상은 탭하지 않아요.
- **준비** — Instagram 로그인

### B7t TikTok 추천 영상 20개 · P2
- **무엇을** — 영상·이미지 캐시를 비우고 추천 피드에서 5초씩 보며 20개를 넘겨요.
- **측정 구간** — 영상 20개 넘기기 → writeback 대기
- **왜** — B7r 과 같은 동작이라 같은 숏폼이라도 앱마다 영상 캐시 Write 가 얼마나 다른지 봐요. Facebook 대신 넣었어요. 추천에 영향을 주지 않게 화면은 탭하지 않아요.
- **준비** — TikTok 첫 실행 동의 창 처리

### B8 Gmail 받은편지함 스크롤 · P2
- **무엇을** — 받은편지함을 30번 내리고 다시 올려요.
- **측정 구간** — 아래로 스크롤 → 위로 스크롤 → writeback 대기
- **왜** — SQLite 위주의 작은 I/O 를 봐요. 메일을 열면 읽음 표시가 남아서 열지 않아요.

### B9 Play 스토어 둘러보기 · P2
- **무엇을** — 캐시를 비우고 홈 추천과 인기 차트를 스크롤해요 (설치 안 함).
- **측정 구간** — 홈 추천 스크롤 → 인기 차트 → 차트 스크롤 → writeback 대기
- **왜** — 아이콘·배너 캐시 Write 를 봐요. 검색 기록을 남기지 않으려고 검색은 하지 않아요.

## C. 미디어 재생

**왜 이 유형인가** — 스트리밍은 네트워크로 받은 버퍼를 디스크에 쓰는 Write 가, 로컬 재생은 순차 Read 가 중심이에요. 화질·구간 이동·오디오로 변형해 버퍼 정책이 I/O 에 미치는 영향을 나눠 봐요.

### C1 YouTube 영상 3분 · P1
- **무엇을** — 검색 결과의 일반 영상을 자동 화질로 3분 재생해요.
- **측정 구간** — 본영상 재생 3분
- **왜** — 스트리밍 재생의 기준이에요. Premium 계정이라 광고가 없어 회차가 같은 조건이에요. 재생 준비는 측정 밖에서 끝내요.

### C2 Shorts 30회 넘기기 · P1
- **무엇을** — Shorts 를 3초씩 보고 넘기기를 30번 해요.
- **측정 구간** — Shorts 30개 넘기기 → writeback 대기
- **왜** — 짧은 영상을 계속 새로 받는 패턴이에요. C1(긴 영상 하나)과 B7r·B7t(다른 앱 숏폼)의 비교 대상이에요.

### C3 로컬 동영상 2분 · P1
- **무엇을** — `setup.sh` 가 만든 2분 영상(`Movies/uxtest_fixture.mp4`)을 캐시를 비우고 시스템 동영상 앱으로 재생해요.
- **측정 구간** — 영상 열기 → 재생 2분
- **왜** — 저장장치에서 영상을 읽는 순차 Read 를 봐요. 스트리밍(C1)과 비교해요. 앱을 지정하지 않으면 앱 선택 창에서 멈춰서 `com.coloros.video` 로 고정했어요.
- **준비** — setup.sh 의 fixture 영상

### C4a YouTube 360p 3분 · P2
- **무엇을** — C1 과 같은 영상을 360p 로 고정해 3분 재생해요.
- **측정 구간** — 360p 재생 3분

## D. 카메라·녹화

**왜 이 유형인가** — 촬영은 사용자가 만드는 가장 큰 Write 예요. 사진은 짧은 burst, 동영상은 일정 대역의 Sequential Write 가 길게 이어져요. 해상도·길이·카메라 방향을 바꿔 대역과 장당 Write 양을 비교해요.

### D1 사진 10장 · P1
- **무엇을** — 워밍업 1장 뒤 2초 간격으로 10장을 찍어요.
- **측정 구간** — 사진 10장 촬영 → 저장 대기
- **왜** — 사진 한 장의 저장 Write 와 그 반복을 봐요. 1초 간격은 처리 중 셔터 입력이 빠져 6장만 저장돼서 2초로 했어요. 모션 사진은 꺼 두고, 워밍업은 첫 장의 초기화 I/O 를 빼려는 거예요.

### D2 버스트샷 3초 · P1
- **무엇을** — 셔터를 3초 길게 눌러 연속 촬영해요 (약 20장, Cshot 폴더).
- **측정 구간** — 셔터 3초 누르기 → 저장 대기
- **왜** — 짧은 시간에 Write 가 몰릴 때의 QD·Latency 를 봐요.

### D3 동영상 30초 1080p · P1
- **무엇을** — 동영상 모드로 바로 열어 1080p 로 30초 녹화해요.
- **측정 구간** — 녹화 시작 → 30초 → 종료 → 저장 대기
- **왜** — 동영상 녹화의 기준이에요 (약 2MB/s). `VIDEO_CAMERA` 인텐트로 열어 모드 전환 UI 를 거치지 않아요.

### D4 동영상 2분 1080p · P2
- **무엇을** — D3 와 같은 조건으로 2분 녹화해요.
- **측정 구간** — 녹화 시작 → 2분 → 종료 → 저장 대기
- **왜** — 오래 이어지는 Write 의 대역과 flush 주기가 일정한지 봐요.

### D5 동영상 30초 4K · P2
- **무엇을** — 해상도를 4K 로 바꿔 30초 녹화하고, 측정 뒤 1080p 로 되돌려요.
- **측정 구간** — 녹화 시작 → 30초 → 종료 → 저장 대기
- **왜** — D3(1080p)와 대역을 비교해요. 해상도 변경과 원복은 측정 밖이에요.

### D6 사진 5장 → 바로 갤러리 · P2
- **무엇을** — 사진 5장을 찍자마자 최근 사진 버튼으로 뷰어에 들어가 5장을 넘겨 봐요.
- **측정 구간** — 5장 촬영 → 최근 사진 열기 → 뷰어 로딩 → 5장 넘기기 → writeback 대기
- **왜** — 저장 Write 직후의 Read 와 썸네일 생성이 겹칠 때를 봐요.

### D7 전면 카메라 사진 5장 · P2
- **무엇을** — 전면 카메라로 바꿔 2초 간격으로 5장을 찍어요.
- **측정 구간** — 사진 5장 촬영 → 저장 대기
- **왜** — D1(후면)과 장당 Write 양을 비교해요. 측정 뒤 후면으로 되돌려요.

### D8 사진↔동영상 모드 전환 ×5 · P2
- **무엇을** — 촬영 없이 사진·동영상 모드만 5번 오가요.
- **측정 구간** — [×5: 동영상 모드 → 대기 → 사진 모드 → 대기] → writeback 대기
- **왜** — 카메라 앱 자체의 I/O(설정·모델 파일 Read) 기준선이에요. D1~D3 에서 이 값을 빼면 촬영 자체의 몫이 남아요.

### D9 화면 녹화 1분 · P2
- **무엇을** — `screenrecord` 로 1분 녹화하면서 설정 화면을 스크롤해요.
- **측정 구간** — 화면 녹화 1분 (스크롤하며) → writeback 대기
- **왜** — 카메라가 아닌 영상 생성 Write 를 D3 와 비교해요. 녹화 중 화면이 계속 바뀌도록 스크롤해요.

## E. 저장공간·파일

**왜 이 유형인가** — 복사·설치·삭제는 앱 UI 보다 파일시스템과 저장장치 동작이 그대로 드러나요. 큰 Sequential Write, 메타데이터 Write, Discard(UNMAP)가 언제 나가는지를 직접 봐요. 원본 파일 생성처럼 측정 대상이 아닌 일은 측정 밖에서 해요.

- **왜** — G1·G2(1000장 전체)와 비교할 일상 사용 기준선이에요. 기기에 다른 사진이 없어 NASA 세트 위에서 재요.
- **준비** — NASA 세트 1000장

### E2 512MB 파일 복사 · P1
- **무엇을** — `/sdcard`(FUSE 경유)에서 512MB 파일을 셸로 복사해요.
- **측정 구간** — 512MB 복사 → writeback 대기
- **왜** — 큰 Sequential Read+Write 의 기준이에요. 원본 생성과 캐시 비우기는 측정 밖이에요.

### E3 앱 재설치 (pm install) · P1
- **무엇을** — 설치된 Instagram 의 APK(분할 포함)를 그대로 다시 설치해요 (`-r`, 데이터 유지).
- **측정 구간** — 재설치 → dexopt 대기
- **왜** — 앱 설치·업데이트의 APK 복사와 dexopt Write 를 봐요. 같은 버전이라 앱 상태는 바뀌지 않아요.

### E4 캐시 정리 trim-caches · P1
- **무엇을** — YouTube·Chrome 캐시를 채운 뒤 전체 앱 캐시를 비워요.
- **측정 구간** — trim-caches → Discard 대기
- **왜** — 많은 파일 삭제의 메타데이터 Write 와 Discard 가 나가는지 봐요. 캐시 채우기는 측정 밖이에요.

### E5 작은 파일 1000개 생성·삭제 · P2
- **무엇을** — `/sdcard`(FUSE)에 4KB 파일 1000개를 만들고 지워요.
- **측정 구간** — 1000개 만들기 → 대기 → 1000개 지우기 → writeback 대기
- **왜** — 데이터(4MB)보다 메타데이터(node·checkpoint) Write 가 얼마나 되는지 봐요.

### E6 1GB 파일 삭제 · P2
- **무엇을** — 1GB 파일을 측정 밖에서 만들고, 지우는 것만 재요.
- **측정 구간** — 1GB 파일 지우기 → Discard 대기
- **왜** — 큰 파일 삭제 때 UNMAP(Discard)이 바로 나가는지, E4 처럼 안 나가는지 확인해요.

### E7 파일 관리자로 256MB 복사 · P2

### E8 Chrome 100MB 다운로드 · P2
- **무엇을** — 공개 속도 시험 파일(OVH 100MB)을 Chrome 으로 받아요.

## G. 갤러리 (NASA 1000장)

**왜 이 유형인가** — 사진이 많을 때 썸네일 생성(Write)과 원본 디코딩(Read)이 스크롤·넘김 속도를 따라가는지가 체감 끊김(jank)과 바로 이어져요. 그래서 G 는 fsiotrace 와 함께 Perfetto FrameTimeline·gfxinfo 를 같이 남겨 I/O 와 jank 를 겹쳐 봐요. 사진은 퍼블릭 도메인 NASA 사진 1000장을 써서 누구나 같은 세트로 재현할 수 있어요 (`dataset/nasa/push.py`).

**공통 준비** — NASA 1000장 푸시, 갤러리 첫 실행 화면 완료. 1회차를 cold(썸네일 미생성)로 보려면 `push.py --repush` 직후에 돌려요. 2·3회차는 warm 이에요.

### G1 그리드 처음→끝 · P1
- **무엇을** — 1000장 그리드를 끝까지 스크롤해요 (4열 기준 약 250줄).
- **측정 구간** — 그리드 처음→끝 → writeback 대기
- **왜** — 썸네일 생성 Write(cold)와 썸네일 Read(warm)를 한 시나리오에서 비교해요.

### G2 뷰어 1→1000장 · P1
- **무엇을** — 뷰어에서 0.5초 간격으로 다음 사진을 999번 넘겨요.
- **측정 구간** — 다음 사진 999장 → writeback 대기
- **왜** — 원본 디코딩 Read 와 jank 를 같이 봐요. 약 12분이라 Perfetto 는 가벼운 설정(FrameTimeline + I/O 대기 사유)을 써요.

### G3 그리드 빠른 fling · P2
- **무엇을** — G1 과 같은 그리드를 짧고 빠른 fling 으로 끝까지 가요.
- **측정 구간** — 그리드 빠른 fling → writeback 대기
- **왜** — 썸네일 Read 가 몰릴 때 QD 와 jank 를 봐요. G1(천천히)과 비교해요.

### G4 뷰어 빠른 넘기기 300장 · P2
- **무엇을** — G2 보다 빠르게(0.15초 간격) 앞 300장을 넘겨요.
- **측정 구간** — 다음 사진 300장 빠르게 → writeback 대기
- **왜** — 원본 Read 가 화면을 못 따라갈 때 jank 와 겹치는지 봐요.

### G5 사진 20장 확대 · P2
- **무엇을** — 사진마다 두 번 탭으로 확대해 옮겨 본 뒤 다음 사진으로 넘어가요 (20장).
- **측정 구간** — [×20: 확대 → 타일 로딩 → 이동 → 원래 크기 → 다음 사진] → writeback 대기
- **왜** — 원본의 부분(타일) Read 를 봐요. `input` 으로는 두 손가락 확대가 안 돼 두 번 탭으로 대신해요.

### G6 20장 삭제 → 휴지통 비우기 · P2
- **무엇을** — 사진 탭 맨 앞 20장을 지우고 최근 삭제된 항목을 비워요.
- **측정 구간** — 20장 선택 → 삭제 → 휴지통 이동 → 최근 삭제된 항목 → 모두 삭제 → writeback 대기
- **왜** — 사진 삭제의 두 단계(휴지통 이동 = 메타데이터, 영구 삭제 = 파일 삭제·Discard)를 봐요. 회차마다 20장씩 줄어 3회 뒤 940장이 남아요. `measure_p2.sh` 가 끝난 뒤 `push.py` 로 빠진 60장만 다시 넣어요.

## S. 대기

**왜 이 유형인가** — 사용자가 아무것도 하지 않아도 동기화·로그·유지보수 작업이 저장장치에 써요. 화면 꺼짐, doze, 화면 켜짐 상태별 배경 I/O 를 나눠 봐요. USB 를 꽂으면 충전 때문에 doze 에 들어가지 않아서 무선 adb 로 재요.

**공통 준비** — 무선 adb 연결(USB 분리, 충전 없음), `UX_DEVICE=<ip:port> UX_SERIAL=<ip:port>`. 측정 앞뒤로 대기 상태와 배터리를 기록해요. 밤에 돌릴 때는 OxygenOS 배터리 앱의 Deep Sleep mode 를 꺼 둬요 (학습된 수면 시간대에 Wi-Fi 를 꺼서 측정이 끊겨요).

### S1 화면 꺼짐 대기 30분 · P3
- **무엇을** — 앱 4개(YouTube·Chrome·Gmail·지도)를 띄워 둔 뒤 화면을 끄고 30분 둬요.
- **측정 구간** — 화면 꺼짐 대기 30분
- **왜** — 기기가 스스로 light/deep doze 로 들어가는 동안의 배경 I/O 예요. 실제 사용에 가장 가까운 대기예요.

### S2 강제 deep doze 30분 · P3
- **무엇을** — S1 과 같은 상태에서 화면을 끄자마자 deep doze 로 강제 진입시키고 30분 둬요 (`dumpsys deviceidle force-idle deep`).
- **측정 구간** — deep doze 대기 30분
- **왜** — doze 중에는 정비 구간(maintenance window) I/O 만 남는지 봐요. S1 과의 차이가 doze 진입 전 구간의 몫이에요. 끝나면 강제 상태를 풀어요.

### S3 화면 끈 직후 5분 · P3
- **무엇을** — 앱 4개를 띄워 둔 채 측정을 켜고 화면을 끈 뒤 5분 둬요.
- **측정 구간** — 화면 끄기 → 5분
- **왜** — 화면을 끄는 순간 앱·시스템이 상태를 저장하는 Write 와 초반 배경 I/O 를 봐요. S1 은 화면을 끈 뒤 측정을 시작해서 이 부분이 빠져 있어요.

### S4 화면 켜진 홈 대기 10분 · P3
- **무엇을** — 앱 4개를 띄워 둔 뒤 홈 화면을 켜 둔 채(`svc power stayon true`) 아무 입력 없이 10분 둬요.
- **측정 구간** — 홈 화면 대기 10분
- **왜** — S1 과 비교할 화면 켜짐 기준선이에요. 끝나면 stayon 을 꺼요.

### S5 아무것도 안 하는 대기 3시간 · P3
- **무엇을** — 앱을 따로 띄우지 않고(앞 측정에서 남은 상태 그대로) 홈에서 화면을 끄고 3시간 둬요.
- **측정 구간** — 아무것도 안 하고 3시간
- **왜** — 오래 둘 때의 배경 I/O(동기화·로그·유지보수 작업)와 doze 정비 구간 주기를 봐요. S1(30분)보다 길게 둬서 긴 주기의 작업까지 담아요. 시간이 길어 1회만 재고, 밤새 돌리는 용도예요.

### S6 야간 충전 대기 6시간 · P3
- **무엇을** — 밤에 충전기를 꽂아 둔 채 화면을 끄고 6시간 둬요. 측정 앞뒤로 충전 상태, f2fs dirty·free segment, idle maintenance 기록을 남겨요.
- **측정 구간** — 충전하며 6시간 대기
- **왜** — Android idle maintenance(fstrim → Discard, f2fs `gc_urgent` → GC)는 기기가 idle 이면서 충전 중일 때 돌아요. 배터리 대기(S1·S5)에는 거의 안 나와서 실제 사용자의 밤 I/O 를 따로 봐요. 이 시나리오만 USB 를 꽂고 재요(`measure_night.sh`, 기본 USB adb). 1회만 재요.

## 검증용

### clock offset 검증 (fsio UFS) · SMOKE
- **무엇을** — 스텝 사이에 `dd` 로 64MB Write 를 한 번 일으켜요.
- **측정 구간** — sleep → dd → sleep → shell
- **왜** — 그 I/O 가 Behavior 탭에서 dd 스텝 행에만 잡히는지 확인해요. clock offset 이 틀리면 옆 구간으로 새거나 통째로 밀려요. 판단 기준은 sleep 구간이 0 인지가 아니에요 (백그라운드 앱이나 f2fs GC 가 I/O 를 낼 수 있어요). 64MB 가 dd 행에 잡히는지를 봐요. 본 측정 전에 돌려요.
